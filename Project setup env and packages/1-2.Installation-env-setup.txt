------------------------
venv = lightweight isolation (Backend apps, APIs)
conda = heavy dependency management (ML / Data Science)
poetry = modern package manager (Production apps)
docker = production isolation
virtualenv = legacy

🧠 Real-World Recommendation
Backend projects → venv or poetry
Microservices → venv + Docker
Learning ML → conda

🧠 Pro Developer Setup (Clean Strategy)
💻 For Web Projects
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt

📦 For Scalable Projects
poetry init
poetry install

🤖 For ML Projects
conda create -n ml python=3.12
conda activate ml

There are multiple ways to create python environment:
1. Built-in python(3.3+): venv
    commands:
        python3 -m venv .venv
        | Part                | Meaning                                                                                                                             |
        | ------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
        | `python3`           | The Python **interpreter** (specifically Python version 3.x).                                                                       |
        | `-m`                | “Run a module as a script.” So instead of running a `.py` file, we’re running a **Python module** (in this case, `venv`).           |
        | `venv`              | The **module name** — part of Python’s standard library since Python 3.3. It creates virtual environments.                          |
        | `.venv`             | The **directory name** where the new virtual environment will be created. You can name it anything (e.g., `venv`, `env`, `myenv`). |

        .venv/
         ├── bin/           # contains the python and pip executables
         ├── lib/           # contains installed packages
         ├── include/       # C headers (rarely needed)
         └── pyvenv.cfg     # config file for environment

        // To activate above environment
        source .venv/bin/activate

    Project Structure:
        my_project/
         ├── .venv/
         ├── main.py
         └── requirements.txt

    Best use case / pros:
     - Creates a folder with:
        isolated site-packages
        Python binary copy/symlink
     - No dependency solver (uses pip only)
     - Backend apps / Microservices / Simple projects   

    Cons:
     - Cannot manage non-Python dependencies (like CUDA, system libs)
     - Dependency conflicts handled manually

2. Using conda
    // stop bydefault activation of base env after installing miniconda
    conda config --set auto_activate_base false

    1. To activate conda base environment
        conda activate

    2. Create a new environment
        a. To create environment at global level
            conda create -n myenv python=3.12
            -n (name)
                → Environment stored in conda global envs directory
                → Activate using:
                    conda activate myenv

            -p (path)
                → Environment created at specific folder instead of global env list
                → Activate using:
                    conda activate ./basic_env   (or full path)

        b. To create project-level environment setup
            cd /CODE/PythonCore/CondaEnv
            conda create -p basic_env python=3.12
                -p (path)
                    → Creates environment at a specific folder (project-local)

                Activation (inside same folder):
                    conda activate ./basic_env   ✅ recommended
                    conda activate basic_env/    ⚠️ may work but not preferred
                    conda activate basic_env     ❌ can cause confusion

                Why use "./" ?
                    - Explicitly tells Conda this is a path
                    - Avoids conflict with named environments like this:
                        conda create -n basic_env python=3.10
                        conda create -p ./basic_env python=3.12

                        and if someone runs conda activate basic_env it confusing
                    - More reliable across systems

                Rule:
                    Always use explicit path when using -p

    basic_env/
     ├── bin/           # python, pip, executables (Linux/Mac)
     ├── lib/           # installed packages
     ├── include/       # headers
     ├── share/         # shared resources
     ├── conda-meta/    # 🔥 VERY IMPORTANT (Conda metadata)

        conda-meta/ folder(This is what makes Conda different from venv)
            Tracks installed packages
            Tracks versions + dependencies
            Enables safe upgrades/removals

    my_project/
     ├── basic_env/        # path-based conda env (like .venv)
     ├── main.py
     ├── environment.yml   # dependency file (conda)
     └── README.md

    Best use case / pros:
     - Designed for data science & scientific computing
     - Handles Python + non-Python dependencies
     - Inbuilt package manager (conda)
     - Dependency solver (very powerful)
     - Precompiled binaries (no build issues)
     - Machine Learning / AI
     - Data Science
     - When using:
        - TensorFlow / PyTorch
        - NumPy with MKL
        - CUDA / GPU
     - Cross-language dependencies (C, Fortran libs)

    Cons:
     - Heavy so not ideal for lightweight backend apps
     - slower than venv
